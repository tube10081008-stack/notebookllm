## 0. 가장 큰 문제: 계측이 없다

Gemini API는 모든 응답에 `usageMetadata`(promptTokenCount/candidatesTokenCount)를 돌려주지만,
현재 코드는 **이를 버린다** (`src/llm/gemini.js` — 응답에서 text만 추출). 즉 지금의 "비용 과다"는
느낌이고, 어떤 연산이 얼마를 쓰는지 아무도 모른다. 이 리포트의 모든 처방보다 **계측(M1)이 선행**이다 —
검색 품질을 eval로 잡았듯, 비용도 숫자로 잡는다.

## 1. 비용 해부 — 연산별 토큰 추정 (코드 근거)

### 1-1. 질의 `/query` — 상시 비용의 주범

| 구성 요소 | 코드 근거 | 크기 (지유=analytical 기준) | 추정 토큰 |
| --- | --- | --- | --- |
| 참고 노트 컨텍스트 | `answer.js:37` — 노트당 `slice(0, 2000)` **고정** | topK 10 (`personas.js:83`) × 2,000자 = 20,000자 | **~10,000** |
| 대화 메모리 | `answer.js:42-46` — 최근 10개 × (질문+답변 500자) | ~6,000자 | ~3,000 |
| 시스템 프롬프트(페르소나+인용규칙) | `answer.js` system | ~1,800자 | ~900 |
| 출력(JSON 답변) | — | — | ~600-1,000 |

**질의 1회 ≈ 입력 14k + 출력 1k ≈ 15k 토큰.** 하루 20회 질문이면 30만 토큰/일.
analytical·methodical·curious 페르소나(topK 10)가 최대치를 상시 소비한다.

### 1-2. 콜드 스타트 재임베딩 — 숨은 반복 비용 (심각)

`retrieve.js:30 ensureVectorStore`: GitHub 영속 모드에서 서버리스 인스턴스가 재활용될 때마다
**전체 노트를 처음부터 재임베딩**한다. 노트 300개 × ~250토큰 = **콜드 스타트 1회당 ~75k 임베딩 토큰**.
Vercel은 하루에도 수차례 콜드 스타트하므로, 지식이 쌓일수록(10년 목표!) **선형으로 악화되는 반복 비용**이다.
설계 의도(불변식 2: 벡터는 재구축 가능)는 옳았지만, "가능"과 "매번"은 다르다.

### 1-3. 수집(ingest)

| 구성 | 코드 근거 | 추정 |
| --- | --- | --- |
| 증류 입력 | `distill.js:72` — `slice(0, 15000)` | ~7,500 토큰/소스 |
| 링크 제안 | `ingest.js:89` — **개념 노트당 LLM 1콜** (노트 5개=5콜) | ~1k×5 = 5k |
| 분류 폴백 | 애매 구간만, 2,500자 샘플 | 0~1.3k (통제됨 ✅) |
| 임베딩 | 노트/조각당 1회, 하이브리드는 2배 | 참고 50조각 시 ~22k 임베딩 |

### 1-4. YouTube 영상 분석 — 단발 최대 비용

`transcribeVideo`(자막 실패 폴백)는 Gemini가 영상을 통째로 시청 — 영상 토큰은 대략 **초당 ~300토큰**,
10분 영상 ≈ **~180k 토큰/건**. 자막 우선 정책은 이미 있으나(✅), 데이터센터 IP에서 자막이 늘 실패하므로
Vercel에서는 사실상 매번 영상 분석 경로를 탄다.

## 2. 설계 모순점 (코드 분석)

| # | 모순 | 근거 |
| --- | --- | --- |
| X1 | **관련도와 무관한 고정 컨텍스트**: 점수 0.9짜리 노트도 0.46짜리도 똑같이 2,000자. 랭킹은 정교하게 해놓고 컨텍스트 예산은 평등 배분 — 랭킹 정보를 버리는 셈 | `answer.js:37` |
| X2 | **혼합(blended) 모드의 자기모순**: "노트가 근거로 부족하다"고 판정하고도 그 부족한 노트들을 **전량(최대 2만자) 전송**한다. 근거로 안 쓸 데이터에 최대 비용 지불 | `answer.js:30-37` |
| X3 | **대화 메모리의 선형 성장**: 오래된 대화도 원문 그대로 재전송. 10번째 질문쯤엔 메모리만 3k 토큰 상시 부담 | `answer.js:42-46` |
| X4 | **재구축 가능 ≠ 매번 재구축**: 벡터 스냅샷을 GitHub에 저장할 수단(`commitFiles` 배치 커밋)이 이미 있는데도 콜드 스타트마다 전량 재임베딩 | `retrieve.js:30` |
| X5 | **링크 제안 N콜**: 같은 소스의 노트 5개가 5번의 독립 LLM 호출 — 후보 목록도 거의 동일한데 프롬프트를 5번 중복 전송 | `ingest.js:87-91` |
| X6 | **하이브리드 증류의 이중 지불**: 혼합 문서에서 목록 부분은 어차피 참고 조각으로 보존되는데, 증류 입력 15,000자에 그 목록까지 포함해 LLM에 보낸다 | `ingest.js` + `distill.js:72` |
| X7 | **단일 모델 일괄 적용**: 분류·링크제안 같은 단순 판단과 답변 합성 같은 고난도 작업이 같은 모델·같은 비용 | `config.js` (textModel 하나) |

## 3. 절감 방법론 — 최신 기법 매핑

| ID | 기법 (근거 기술) | 해결하는 모순 | 예상 절감 | 난이도 |
| --- | --- | --- | --- | --- |
| **M1** | **토큰 계측**: `usageMetadata`를 이벤트로 적재 + `/api/usage` 집계 (연산별·스테이션별) | §0 | 절감의 전제 | 하 |
| **M2** | **관련도 비례 컨텍스트 예산**: 총예산(예: 6,000자)을 점수 비례로 배분. blended면 노트 제목+한줄만 | X1, X2 | 질의 입력 **-50~65%** | 하 |
| **M3** | **롤링 요약 메모리**: 답변 저장 시 1줄 요약을 함께 저장(chats.jsonl에 `summary`), 메모리는 최근 2개만 원문 + 나머지는 요약 | X3 | 메모리 **-70%** | 중 |
| **M4** | **벡터 스냅샷 영속화**: ingest 후 `vectors.json`을 배치 커밋에 동승, 콜드 스타트는 스냅샷 로드 + 누락분만 재임베딩 | X4 | 콜드스타트 임베딩 **-95%+** (성장 비례 비용 → 상수화) | 중 |
| **M5** | **링크 제안 배치**: 소스당 새 노트 전부를 1콜로 (신규 노트 목록 + 후보 목록 → 관계 배열) | X5 | 링크 호출 **-80%** | 하 |
| **M6** | **증류 입력 다이어트**: hybrid에서 항목 런(목록 블록)을 제거한 산문만 증류에 전달 (`reflowLines`/`isEntry` 재사용) | X6 | 혼합 소스 증류 입력 **-30~60%** | 하 |
| **M7** | **암시적 프롬프트 캐싱 정렬**: Gemini implicit caching은 반복되는 프리픽스를 자동 할인 — 시스템·규칙(정적)을 앞에, 노트·질문(동적)을 뒤에 고정. 스테이션별 시스템 프롬프트는 이미 안정적이라 적합 | 전반 | 반복 프리픽스 **-75% (캐시분)** | 하 |
| **M8** | **모델 티어링**: `LLM_LIGHT_MODEL`(flash-lite급)을 분류·링크·스카우트에, 본 모델은 답변·증류에 | X7 | 보조 호출 **-60~70%** | 중 |
| **M9** | **영상 절약 모드**: `mediaResolution: low` 지정 + 장영상(>15분) 사전 경고, 요약형 지시 유지 | §1-4 | 영상 건당 **-50~70%** | 하 |

## 4. 우선순위 로드맵

```
P0  M1 계측            — 이후 모든 절감을 숫자로 검증할 기반 (이 프로젝트의 원칙)
P1  M4 벡터 스냅샷      — 10년 축적과 정면충돌하는 유일한 "성장 비례" 비용 제거
P1  M2 컨텍스트 예산    — 상시 비용의 최대 항목, 코드 소폭
P2  M5 링크 배치 · M6 증류 다이어트 · M7 캐싱 정렬 — 수집 비용 일괄 절감
P3  M3 롤링 요약 · M8 모델 티어링 · M9 영상 절약
```

**합산 기대 효과 (보수 추정):** 질의 -50%↑, 수집 -40%↑, 콜드스타트 임베딩 -95%,
전체 월 비용 **-55~70%**. 단 — 이 수치들은 가설이며, M1 계측 배포 후 1주 실측으로 검증한다.

## 5. 검증 계획

1. M1 배포 → 3일 실측 → 연산별 기준선(baseline) 확정
2. P1 적용 → 동일 워크로드로 재측정 → 절감률 확정
3. 품질 회귀 확인: `npm run eval`(검색) + 답변 품질 스팟체크 — **비용 절감이 품질을 깎으면 롤백**
   (특히 M2 예산 축소는 인용 품질과 트레이드오프 가능 → 예산값을 env로 노출해 조정 가능하게)
